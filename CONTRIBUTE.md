# Приём внешних изменений

Внутренний GitLab является источником истины для OpenLogReplicator. GitHub
используется для публикации исходного кода и приёма предложений от сообщества.
Основная ветка GitHub обновляется только через push mirror из GitLab.

Этот документ предназначен для участников проекта. Общие рекомендации для
внешних авторов находятся в [`CONTRIBUTING.md`](CONTRIBUTING.md).

## Приём GitHub PR

Внешний PR не следует сливать напрямую в основную ветку GitHub. Его изменения
сначала переносятся во внутренний GitLab:

1. Проверить описание, лицензионную чистоту и содержимое PR. Не загружать во
   внутренний контур непроверенные бинарные файлы, дампы, ключи, пароли и
   закрытые данные.
2. Создать рабочую ветку от актуальной целевой ветки внутреннего GitLab.
3. Получить коммиты PR из публичного репозитория и применить их в рабочей
   ветке.
4. При необходимости адаптировать изменение, сохранив исходное авторство.
5. Отправить рабочую ветку в GitLab и создать внутренний MR со ссылкой на
   GitHub PR.
6. Выполнить внутренние проверки CI и провести ревью кода.
7. После слияния внутреннего MR дождаться публикации коммита через GitLab push
   mirror.
8. Если GitHub не распознал PR как принятый после публикации, закрыть его со
   ссылкой на опубликованный коммит и поблагодарить автора.

## Перенос коммитов

Команды выполняются в клоне внутреннего репозитория. Вместо значений в угловых
скобках указываются фактические номер PR и целевая ветка:

```bash
git fetch origin <target-branch>
git switch -c community/pr-<pr-number> origin/<target-branch>
git fetch https://github.com/tarantool/OpenLogReplicator.git \
  pull/<pr-number>/head:github-pr-<pr-number>
git log --reverse --oneline \
  origin/<target-branch>..github-pr-<pr-number>
git rev-list --merges \
  origin/<target-branch>..github-pr-<pr-number>
git cherry-pick <commit-1> <commit-2> <commit-N>
git push -u origin community/pr-<pr-number>
```

Коммиты передаются в `git cherry-pick` в порядке от старого к новому, который
показывает `git log --reverse`. Для одного коммита используется
`git cherry-pick <commit>`. Если `git rev-list --merges` вывел коммиты слияния,
нельзя применять весь диапазон вслепую: следует выбрать содержательные
изменения или подготовить набор изменений на основе разницы между целевой
веткой и веткой PR.

Для OpenLogReplicator-docker используется тот же процесс, но PR получается из
`https://github.com/tarantool/OpenLogReplicator-docker.git` и отправляется во
внутренний репозиторий `openlogreplicator-docker-vk`.

Если PR нельзя перенести целиком, допустимо применить отдельные коммиты или
набор изменений. В этом случае в итоговом коммите сохраняется автор исходного
изменения либо добавляется служебная строка:

```text
Co-authored-by: Contributor Name <contributor@example.com>
```

Внутренний MR должен содержать ссылку на исходный GitHub PR и кратко объяснять
адаптации, сделанные при переносе.

## Обновление внешнего PR

Если автор добавил коммиты до слияния внутреннего MR, сопровождающий проекта
получает их и применяет в той же рабочей ветке. Уже перенесённые коммиты
повторно не применяются.

Если внутренний MR уже слит, новые изменения оформляются отдельной рабочей
веткой и отдельным внутренним MR.

## Расхождение основных веток

Нельзя исправлять расхождение принудительной отправкой (`force push`). Следует
временно остановить изменения основных веток, объединить актуальные истории в
рабочей ветке GitLab, провести проверки CI и ревью кода и выполнить штатное
слияние в GitLab. После этого push mirror опубликует объединённую историю в
GitHub.

Архитектурное обоснование процесса приведено в
[`ADR-0001`](documentation/spec/adr/0001-repository-synchronization.md).
