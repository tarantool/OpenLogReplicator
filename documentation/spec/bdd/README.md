# BDD — Behaviour-Driven Development

BDD-сценарии описывают **как продукт ведёт себя** в человекочитаемом виде и
служат мостом между [PRD](../prd/) и тестами. Сценарии пишутся так, чтобы их мог
понять любой участник проекта: разработчик, тестировщик, аналитик, руководитель
проекта или заказчик. Для автоматического выполнения сценариев нужен
инструмент, который читает `.feature`-файлы и запускает описанные в них шаги как
тесты.

## Назначение

- Зафиксировать наблюдаемое поведение функциональности, привязанное к пользовательскому пути из PRD.
- Дать основу для исполняемой спецификации: после настройки автоматического
  запуска один и тот же сценарий читается человеком и выполняется как тест.
- Упростить ревью: проверять «что должна делать система» по сценарию быстрее, чем по коду и unit-тестам.

## Когда писать BDD

- Есть PRD, описывающий пользовательский путь, и его поведение можно проверить через наблюдаемые границы (HTTP, UI, CLI, выходной топик/очередь).
- Сценарий описывает критически важный пользовательский путь: если он перестанет
  работать, пользователь не сможет выполнить основную задачу либо возникнут
  финансовые, операционные или репутационные потери.
- Поведение пересекает несколько модулей и его сложно удержать в голове по unit-тестам.

## Формат файла

Имя файла: `kebab-case-slug.feature` (предпочтительно для Cucumber) или
`kebab-case-slug.md`, если автоматический запуск сценариев пока не настроен.

Шаблон сценария (Cucumber Gherkin):

```gherkin
# language: ru

Функция: <Краткое название поведения>
  Связанный PRD: ../prd/<NNNN>-<slug>.md
  Связанный ADR: ../adr/<NNNN>-<slug>.md (если применимо)

  Сценарий: <Что проверяем>
    Допустим <предусловие>
    Если <действие пользователя или системы>
    Тогда <наблюдаемый результат>
    И <дополнительное ожидание, если есть>
```

Допустимо использовать английский (`Feature`/`Scenario`/`Given`/`When`/`Then`)
— язык выбирается один раз на проект и фиксируется в конфигурации инструмента,
который запускает BDD-сценарии.

## Чего в BDD быть не должно

- Деталей реализации (имена классов, формат внутренних структур) — только наблюдаемое поведение.
- Проверок, которые дублируют unit-тесты и не дают продуктовой ценности.
- Обращений к внутренним слоям напрямую (например, к БД из E2E BDD), если это явно не разрешено ADR. Иначе тест перестаёт быть «поведением продукта».

## Связи с другими разделами

- Каждый сценарий ссылается на PRD, чьё поведение описывает.
- Если сценарий опирается на архитектурное правило — ссылка на ADR.
- После настройки автоматического выполнения команда запуска фиксируется в
  этом README и добавляется в CI. Сейчас BDD-сценарии в проекте автоматически
  не запускаются.

## Эволюция формата

Пока автоматический запуск не настроен, первые сценарии можно писать как
`.feature` без исполнения. Выбор инструмента запуска и добавление обязательной
проверки в CI оформляются отдельным ADR.
