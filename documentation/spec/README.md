# Spec

Каталог для документов, фиксирующих решения на разных уровнях: архитектурном, продуктовом и поведенческом. Цель — снизить потерю контекста у людей и AI-агентов, дав явные ссылки на «почему» и «как должно работать».

## Разделы

- [`prd/`](prd/) — Product Requirements Documents. Зачем существует фича, какую проблему решает, как пользователь проходит сценарий.
- [`adr/`](adr/) — Architecture Decision Records. Почему принято архитектурное решение и как оно поддерживается в коде.
- [`bdd/`](bdd/) — Behaviour-Driven Development. Сценарии поведения продукта
  в человекочитаемом виде, которые после подключения раннера могут исполняться
  как тесты.

## Источник

Раздел структурирован по мотивам доклада «Capturing decisions: ADR, PRD & BDD» — [видео на YouTube](https://www.youtube.com/watch?v=504PvfXou5Y).

## Связи между документами

- ADR ссылается на PRD, если архитектурное решение обслуживает конкретную фичу.
- PRD ссылается на ADR, если фича опирается на архитектурное ограничение.
- BDD-сценарий ссылается на PRD, поведение которого он описывает и на ADR, если в сценарии задействовано архитектурное правило.
- Любой документ может ссылаться на связанный тикет, дизайн-док или иной
  источник требований.

## Оформление

Порядок разделов (заголовков) внутри документа — не строгий: важна полнота и содержание, а не точная последовательность секций. Располагай их так, как удобнее читать в конкретном документе.

Относительные ссылки используются только для файлов внутри репозитория и должны
разрешаться из каталога документа. Для ресурсов вне репозитория используются
абсолютные ссылки.
