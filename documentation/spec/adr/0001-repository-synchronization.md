# Синхронизация внутренних GitLab-репозиториев с GitHub

## Контекст

Разработка OpenLogReplicator и OpenLogReplicator-docker ведётся во внутреннем
GitLab. Публичные репозитории GitHub должны регулярно получать проверенные
изменения и релизные теги. Внешние pull request создаются в GitHub, но
изменения из них должны пройти внутренние CI и ревью до включения в основную
ветку.

## Решение

Внутренний GitLab принимается за единственный источник истины и место слияния
изменений. GitHub используется для публикации кода и приёма внешних PR, но
основная ветка GitHub напрямую не изменяется.

Для обоих репозиториев настраивается встроенный GitLab push mirror в
соответствующий репозиторий GitHub:

- зеркало регулярно публикует изменения разрешённых веток;
- публикуются только явно разрешённые защищённые ветки;
- публикуются защищённые релизные теги по шаблону, принятому в каждом
  репозитории;
- внутренние и временные ветки не публикуются;
- для доступа используется отдельный технический пользователь с минимальными
  правами на запись;
- основные ветки GitHub защищаются от прямого изменения; запись разрешается
  только технической учётной записи зеркала.

Внешний PR проверяется в GitHub, но не сливается там. Сопровождающий проекта
забирает исходные коммиты PR через `cherry-pick` или применяет присланные
изменения в рабочей ветке внутреннего GitLab. Затем он создаёт внутренний MR,
выполняет внутренние проверки CI и проводит ревью кода. После слияния
внутреннего MR GitLab push mirror публикует итоговую историю в GitHub. Внешний
PR закрывается со ссылкой на опубликованный коммит и с указанием, что изменение
принято.

Исходные коммиты по возможности переносятся без изменения, чтобы сохранить
авторство. Если изменение приходится адаптировать или объединять, авторство
фиксируется через `Co-authored-by`. Подробный процесс описан в
[`CONTRIBUTE.md`](../../../CONTRIBUTE.md).

Изменение, инициированное внутри компании, проходит действующий процесс
разработки: рабочая ветка, MR, проверки CI и ревью кода во внутреннем GitLab.
После слияния push mirror публикует изменение в GitHub. Внутренняя задача
хранит ссылки на GitLab MR и опубликованный коммит.

Сообщения коммитов, попадающих в публичную историю, должны быть понятны без
доступа к внутренним системам и не должны содержать внутренние ссылки или ключи
задач. Ссылка на внутреннюю задачу фиксируется в описании GitLab MR. Если для
изменения создана публичная задача GitHub, в сообщении коммита можно указать её
номер.

Одинаковая схема применяется к обеим парам репозиториев:

- внутренний `openlogreplicator` ↔ публичный `OpenLogReplicator`;
- внутренний `openlogreplicator-docker-vk` ↔ публичный
  `OpenLogReplicator-docker`.

Для каждой пары отдельно задаётся соответствие основных веток. Синхронизация
одного репозитория не должна запускать обновление другого.

Перед включением зеркала вся публикуемая история проверяется на секреты,
внутренние адреса и конфиденциальные файлы.

## Как поддерживается

- GitLab push mirror публикует разрешённые ветки и релизные теги в GitHub.
- Настройки защиты ветки GitHub запрещают прямой push в основную ветку, кроме
  технической учётной записи зеркала.
- Ревью кода проверяет, что внешний PR перенесён в GitLab с сохранением
  авторства и прошёл внутренние проверки.

## Как исправлять расхождение

Если push mirror обнаружил расхождение основных веток:

1. Запретить новые изменения основных веток обоих репозиториев на время
   восстановления.
2. Получить актуальные ветки GitLab и GitHub и определить общее основание.
3. Создать рабочую ветку от актуальной ветки GitLab и влить в неё актуальную
   основную ветку GitHub.
4. Провести обязательные проверки и ревью кода во внутреннем GitLab.
5. Обновить основную ветку GitLab штатным слиянием. Push mirror опубликует
   объединённую историю в GitHub.
6. Убедиться, что основные ветки указывают на один коммит, затем снять запрет
   на изменения.

Принудительная отправка (`force push`) в основные ветки при восстановлении не
используется.

## Последствия

Преимущества:

- GitLab и GitHub сохраняют одну линейку опубликованной истории;
- публикация не зависит от раннера CI;
- теги и история коммитов сохраняются;
- внешние изменения проходят внутренние CI и ревью.

Ограничения:

- перенос внешнего PR требует ручных действий сопровождающего проекта;
- GitHub может не распознать перенесённый PR как принятый; в этом случае он
  закрывается вручную со ссылкой на опубликованный коммит;
- комментарии, согласования и статусы проверок GitHub не переносятся во
  внутренний MR;
- GitHub Release создаётся отдельно, поскольку зеркало переносит тег, но не
  объект релиза.

## Альтернативы

Автоматическая обратная синхронизация через GitHub Actions отклонена: она
требует доступа раннера к внутреннему GitLab, хранения внутренних секретов в
GitHub и обработки расхождения веток.

Слияние внешнего PR напрямую в GitHub с последующим `cherry-pick` в GitLab
отклонено: обычное слияние или объединение коммитов (`squash`) создаёт другой
головной коммит, после чего push mirror не сможет обновить GitHub как
fast-forward.

Безусловная двусторонняя синхронизация отклонена из-за риска конфликтов,
циклических обновлений и перезаписи истории.
